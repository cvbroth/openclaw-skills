## VL 调用位置及单变量修复

原16GiB R5完整堆栈定位：PaddleX3.4.0 `doc_vlm/processors/paddleocr_vl/_paddleocr_vl.py:160`，将 `image_grid_thw[index].prod() // merge_size // merge_size` 传给 `int()`；PaddlePaddle3.2.2 `paddle/base/dygraph/math_op_patch.py:237` 执行 `int(np.array(var))`。这不同于“模块没装”，也不是该次OOM或超时。

原第6页仅加载未修改预处理器、通过trace观察实际调用，确认caller为上述第160行、张量shape=[1]、数组shape=(1,)、size=1，原异常原样发生；这不是成功OCR输出。合成同一表达式也实测：Paddle张量shape=[1]，NumPy数组shape=(1,)，size=1；NumPy2.5.3报相同TypeError。注意这是**单元素但非零维**，不是多元素数组。直接prod返回零维，但floor-div之后成为一维；仅测试prod会漏掉问题。[NumPy2.4官方说明](https://numpy.org/doc/stable/release/2.4.0-notes.html)确认非零维数组转标量自2.4起抛TypeError；[PaddleOCR官方仓库问题17728](https://github.com/PaddlePaddle/PaddleOCR/issues/17728)报告同一调用链，并提出显式item的修复。问题标题“NumPy>=2.0”并不精确，不能照搬为所有2.x不兼容。

候选只将NumPy2.5.3固定为2.3.5，其余包、模型提交、模型哈希、VL配置不变；没有修改安装包源码。已安装包元数据要求Paddle numpy>=1.21、PaddleX>=1.24、SciPy>=2.0,<2.8，因此没有盲目降到1.x。候选pip check通过，同一表达式int结果25。它是本次实测兼容候选，并非宣称官方专门认证这整套组合。`Dockerfile.paddleocr-vl-numpy-compat`与完整候选lock单列，原镜像与证据保留。
